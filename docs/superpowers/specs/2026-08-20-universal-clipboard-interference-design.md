# Design: Universal Clipboard interference mitigation

Date: 2026-08-20

## Background

Reported symptom: on the Mac running SuperDictate, Universal Clipboard
(Continuity) intermittently stops working in the iPhone→Mac direction —
copying on iPhone and pasting on this Mac silently fails to bring over the
iPhone's clipboard content — while Mac→iPhone paste keeps working. The
failure is not constant; it has been observed to clear up after restarting
the `com.local.superdictate.agent` background service (see `AGENTS.md`'s
"Local Installation" invariant for that service name), without any other
system-level intervention (no reboot, no Bluetooth/Handoff toggle).

## Root cause

`ClipboardPasteInserter` (`TextInsertion.swift:1050-1153`) performs **two
full clear+write cycles on `NSPasteboard.general`** — the literal
system-wide general pasteboard, the same one macOS Continuity's `sharingd`
daemon watches via `changeCount` to decide what to advertise/accept across
devices — for every single dictation:

1. `insert(_:)` (line 1062): snapshots the current pasteboard
   (`PasteboardSnapshot.capture`), then `pb.clearContents(); pb.setString(
   dictatedText, forType: .string)` — write #1 — before posting a synthetic
   ⌘V.
2. `restorePasteboard` (line 1105): after confirming (via AX polling, up to
   `confirmationTimeout` = 2.0s) that the paste landed, if nothing else
   touched the pasteboard in the meantime (`changeCount`/string-equality
   guard), calls `snapshot.restore(to: pasteboard)`, which is itself
   `pb.clearContents(); pb.writeObjects(...)` — write #2.

Neither write marks its `NSPasteboardItem` with any of the informal-but-
widely-honored `org.nspasteboard.*` marker types
(`org.nspasteboard.TransientType`, `.ConcealedType`, `.AutoGeneratedType`)
that tell clipboard-history tools and Continuity-adjacent code "this write
is not a real, user-initiated copy, don't treat it as one." Every
clipboard-manager vendor that legitimately needs to write-then-restore the
pasteboard for its own purposes (most directly: password managers doing a
one-shot paste-and-forget, which is structurally identical to what
`ClipboardPasteInserter` does here) uses `org.nspasteboard.TransientType`
for exactly this. SuperDictate currently writes plain `.string` data only,
so from the outside — including to `sharingd` — every dictation looks
indistinguishable from the user manually copying new content twice in a
row.

This was already investigated once, from a different angle: the v0.4.4
"clipboard race fix" (`docs/superpowers/specs/2026-07-29-clipboard-race-
and-number-itn-design.md`) replaced a fixed 0.35s restore delay with the
current AX-confirmation-based wait specifically to avoid clobbering
something the user manually copies *on this same Mac* during the wait
window. That fix's `changeCount` guard is real and correct for that case
(verified by `SelfTest.swift`'s
`skipsRestoreIfPasteboardChangedDuringPoll` test) — but it was never aimed
at, and does not address, cross-device Continuity/Universal Clipboard
interference. That angle was not considered at the time.

Two known-uncertain mechanisms, either of which is consistent with the
reported behavior:

- Apple's own Universal Clipboard implementation is understood to use
  lazily-fulfilled ("promise") pasteboard items for incoming cross-device
  content — a type is declared on the local pasteboard, but actual bytes
  are fetched from the source device only once something actually reads
  them. `PasteboardSnapshot.capture` (line 1163) only ever stores concrete
  `(type, data)` pairs it can read *right now*; it cannot capture a promise
  it hasn't fulfilled. If SuperDictate's `clearContents()` runs while such
  a placeholder is sitting on the general pasteboard, the placeholder is
  destroyed outright, and `restore()` cannot bring it back — it only has
  the earlier concrete snapshot to fall back to.
- Independent of promises: two `clearContents()`-driven ownership changes
  per dictation, dozens of times a day, is exactly the kind of pasteboard
  churn empirically reported (Apple Developer Forums threads, third-party
  clipboard-manager issue trackers) to desynchronize `sharingd`'s internal
  advertise/accept bookkeeping, which has no public API to distinguish "the
  user genuinely copied something" from "an app briefly borrowed the
  pasteboard and gave it back."

`sharingd` is an undocumented system daemon; neither mechanism above can be
proven from application-level code alone, and no unit test can exercise
real Continuity behavior. The fix below is therefore a well-targeted,
low-risk mitigation based on the one lever applications actually have
(the `org.nspasteboard.*` marker convention), not a certainty-backed root
cause fix — see "Verification" below for how to confirm it empirically
over time.

## Fix

1. **Mark the transient dictation write as transient.** Add a `transient:
   Bool = false` parameter to `ClipboardPasteInserter.write(_:to:)`. When
   `true`, build an `NSPasteboardItem` carrying both the `.string` data and
   an empty-data entry for `org.nspasteboard.TransientType`, and write it
   via `pb.writeObjects([item])` instead of `pb.setString(_:forType:)`.
   Default stays `false` so the two existing non-ephemeral call sites are
   unaffected:
   - `ParakeyApp.swift:2382` — the "AX target disappeared mid-dictation,
     save transcript to clipboard so the user doesn't lose it" safety net.
     This content is meant to be pasted manually, possibly much later —
     marking it transient would be actively harmful (risks clipboard-
     manager/Continuity tools treating it as disposable and not making it
     available for a later manual paste).
   - `insert(_:)`'s own call (`TextInsertion.swift:1065`) becomes the one
     call site that passes `transient: true` — this is the only write that
     is genuinely ephemeral (it exists purely to be immediately consumed by
     the synthetic ⌘V posted a few lines later, then reverted).
2. **Leave the restore write (`PasteboardSnapshot.restore`) unmarked, as
   today.** It's putting back the user's real prior clipboard content,
   which should behave exactly like a normal clipboard write to any
   observer. If that prior content already carried its own
   `org.nspasteboard.*` marker (e.g. it came from a password manager),
   `PasteboardSnapshot` already preserves it — the snapshot is generic over
   every `(type, data)` pair present at capture time, so no special-casing
   is needed here.
3. **Add observability for next time.** Log the outcome of each
   transient-write/restore cycle (write succeeded and marked transient;
   restore happened; restore was skipped because the pasteboard changed
   during the wait — which is itself a useful signal, since a same-Mac
   manual copy and an incoming Continuity write look identical at this
   layer). Today `ClipboardPasteInserter` only logs failure paths. If this
   mitigation doesn't fully resolve the reported issue, these log lines
   let a future investigation correlate "Universal Clipboard just broke"
   against SuperDictate's own pasteboard activity timeline from
   `~/Library/Logs/SuperDictate.log`, instead of starting from scratch.

## Non-goals

- No Settings/Control Panel toggle for this — it's a strict improvement
  with no user-facing tradeoff (worst case: `sharingd` ignores the marker
  and behavior is unchanged; best case: it fixes the interference). Adding
  an opt-out would just be an unused knob.
- No attempt to special-case or detect "a Continuity promise is currently
  on the pasteboard" — there's no public API to detect that, and the
  `org.nspasteboard.TransientType` marker is the documented, general-
  purpose way to signal "don't treat this write as real."
- No change to the existing v0.4.4 confirmation-polling/changeCount-guard
  logic — that fix is correct for its own scenario (same-Mac manual copy
  during the wait) and orthogonal to this one.

## Verification

There is no way to unit-test real `sharingd`/Continuity behavior, so this
fix is verified in two layers:

- **Unit tests** (deterministic, in-repo): confirm `write(_:to:transient:)`
  actually attaches `org.nspasteboard.TransientType` when `transient: true`
  and does not when `false` or omitted; confirm the `.string` payload is
  still readable via `NSPasteboard.string(forType:.string)` either way (the
  existing `restorePasteboard` guard and the two non-ephemeral call sites
  depend on that); confirm the two existing non-ephemeral call sites'
  behavior is byte-for-byte unchanged (source-compatible default param).
- **Manual, longitudinal verification** (cannot be automated): after
  installing the fix, dictate normally for a few days of regular use and
  watch whether Universal Clipboard (iPhone→Mac paste) keeps working
  without needing an agent restart. This is inherently a "did the bug stop
  recurring" observation, not a pass/fail test — track it against the new
  log lines from item 3 above if it does recur.
